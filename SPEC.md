# lonewrt: OpenWrt firmware template for the ZTE MF289F, spec

Revision 2026-11-23 · code 3c946f1 · format spec-writing 0.8

## Problem

An LTE router often stands where nobody is around to look after it.
The modem can hang, the data package expires, the SMS store fills up, and a button reset erases the whole configuration.
Without help this ends in long outages that the owner learns about from the people on site.
The image gives a router that comes back configured after a flash and after a button reset, repairs the usual link failures by itself and leaves a trail for diagnosis.
The same code, built from a profile without secrets, gives an image anyone with the same router model can use.
Building it needs a Linux machine, which many people with this router do not have, so they also get a way to build in their own GitHub account from a browser.

## User

- **The owner** builds the image, flashes it and manages the router remotely over a WireGuard tunnel or Tailscale, and optionally over Telegram and SMS.
- **People on site** use the WiFi only; when something fails they may press the reset button.
- **Someone who gets a router with the generic image** has the same router model and their own SIM; they change settings in LuCI (the router's web interface).
- **Someone without a Linux machine**, for example a reader of an OpenWrt forum, has an MF289F that runs OpenWrt and wants an image of their own profile; they have a web browser, a GitHub account and LuCI.
- **A coding agent** that works for an owner builds and checks the image, following the project's agent skill.

## Goal

The owner flashes an image built from a chosen profile onto an MF289F.
The router then comes up by itself, after the flash and after every button reset, with working LTE, WiFi and, when the profile enables it, the tunnel.
An image from a private profile is accepted by the checklist after a flash and a reset test at the router; the generic image by a trial on a router with another operator's SIM (see Acceptance).
Someone without a Linux machine gets the same kind of image from a GitHub repository of their own. The build on GitHub, the configurator and the agent skill are accepted by trials the owner runs on a second GitHub account (see Acceptance).
With Tailscale on, the owner reaches LuCI and SSH by name from their own devices after one sign-in, accepted by point 10 of Acceptance.
The use of IPv4 and IPv6 is accepted by points 11 to 13 of Acceptance, and only an image that has all of its parts may start in the mode that uses both; 0.7.0 starts with IPv4 alone, and that mode becomes the default after it has run on an MF289F with a SIM that gives IPv6.
Its usefulness shows in the first long period without a visit: did link failures end without a person.

## What it does

- **S1.** The owner builds an image from a profile; the generic image holds no secrets and no private data, and private profiles and images never reach git. When passwords are left empty, the build writes a card with the passwords and hints for the person who gets the router. (R1 to R6, R33, R33a)
- **S2.** After a flash or a button reset the router comes up with the settings of its profile, without anyone logging in. (R7 to R9)
- **S3.** At every start the router puts the modem back to LTE-only mode, the profile's bands and the right SMS store, whatever an earlier test left behind; when the profile gives no APN, the router finds one by itself. (R10 to R13)
- **S4.** When the mobile network drops the data session while the modem stays registered, the router starts the session again in place within seconds, without restarting the connection. When the internet goes away for another reason, the router repairs it by itself: first a restart of the connection, then restarts of the whole router at growing intervals, up to a limit. (R49 to R49g, R14 to R21)
- **S5.** When a restart does not bring LTE back, the router switches to slow 2G (EDGE) between restarts so the owner keeps remote access; after the restarts are used up it stays on EDGE and tries LTE again from time to time. (R22 to R25)
- **S6.** Operator SMS (top-ups, package expiry) keep arriving, because the router cleans the SMS store by itself and archives the whole store before it deletes anything. (R26)
- **S7.** The owner sees in the logs and in LuCI what happened: the signal every few minutes, the course of a failure, the modem state, the data usage. A profile can turn on a debug log level for a test period: a longer persistent log, the signal samples in it and every step of the data session repair. (R28 to R30, R29c)
- **S8.** The owner reaches the router over a WireGuard tunnel; in the generic image the tunnel is prepared but disabled. (R31 to R32)
- **S9.** With Telegram keys in the profile, every SMS on the SIM reaches the owner's Telegram chat within seconds, and once a week the router checks the balance and sends a message only when it has fallen below a threshold; from the chat the owner asks for the balance, the link state, the WiFi name and password with a QR code, the devices and the latest SMS, gives the devices names, runs a speed test and restarts the router. The messages are readable for a person without technical knowledge, and after a longer outage the router says the internet is back. Numbers in the profile can also ask for the state and restart the router by SMS. (R34 to R48, R50, R51)
- **S10.** Someone without a Linux machine puts their profile into a private GitHub repository of their own as one secret, starts the build there for the lonewrt release they choose, and downloads the image to flash in LuCI or with a coding agent; the profile sets both passwords, so every build gives the same ones, and it can hold SSH keys for login; a public repository stops the build before anything is uploaded, except a test run with made-up values. (R52 to R55, R61)
- **S11.** The configurator, a web page in one file, shows every profile key that matters for the values given so far, with its meaning and the values of the generic profile, lets the person pick the time zone from a list, loads an existing profile and fills in the keys a newer release added, catches obvious mistakes, draws the two passwords on request, shows what the router would read from an operator's balance SMS, explains how to get the Telegram keys, and gives the profile as text to copy or a file to save, without loading or sending anything. (R56 to R58a)
- **S12.** A coding agent with the agent skill leads its person from no profile to a checked image, built on their machine or on GitHub, without showing a secret of the profile in the chat, and flashes it only after the person says yes, with a backup first. (R59 to R59g)
- **S13.** With Tailscale turned on in the profile, the owner adds the router to their own Tailscale account with one sign-in link: the bot sends it after the flash, and an SMS command or SSH gives it too; a key in the profile adds the router without a click instead. The owner then reaches LuCI and SSH by the router's name from their own devices, with no server of their own. The bot says how to connect, when the sign-in ends and when a reset left an old entry, and the router's LAN can be made reachable as well. (R63 to R71)
- **S14.** The router can use the internet versions the operator gives, IPv4, IPv6 or both: a refused IPv6 does not take the link down, an operator that gives IPv6 only still gives the devices IPv4 by translation, the devices on the WiFi get IPv6 when the operator gives it, and in LuCI the owner can switch this mode on or force one version. 0.7.0 ships with IPv4 alone as its default and this mode switched on in LuCI, until the mode has run on this router with a SIM that gives IPv6; a flash that keeps settings keeps an older image's IPv4 setting until it is changed in LuCI. (R7c, R7d, R73 to R73p, R74 to R76e, R77 to R77d)

## What it does not do

The image does not have these functions and does not cross these lines:

- It does not update the modem firmware.
- It does not recognise the data package, count used GB or raise an alarm during a link failure, because without internet nothing reaches Telegram; the alarm comes from a separate heartbeat on a server (R42), and the router sends a message only once the internet is back (R40).
- It changes nothing on the WireGuard server.
- It does not update itself from LuCI; a new OpenWrt version is a new image build.
- It sends no SMS other than the balance query of the operator preset (with the shipped preset `29702`: `RACUN` to 1466) and the replies to SMS commands, and no USSD codes; the bot changes no state of the router other than the 2G message switch, a restart confirmed with a button and starting a Tailscale sign-in. (R27, R37a)
- The generic image holds no secrets and no data of a private profile. (R4)
- The image's scripts talk to the modem with AT commands only; the one exception is `lw-linkwatch`, which reads the state of the data call and starts it again over QMI while netifd shows the interface up. The QMI handler of netifd, `qmi.sh`, is the file of the OpenWrt package with the build's edits: without its 26-second network scan, and with its own setup of the IP versions. (R12c, R12d, R49a)
- Over IPv6 it lets no new connection from the internet in to the router or the WiFi devices. (R75, R75a)
- It does not remember that an operator refused IPv6; it asks again at every start. (R73c)
- On a SIM that gives IPv6 only, the devices get IPv4 for their own connections only: nothing from the internet reaches them over IPv4 there.
- When one IP version is lost while the other works, it does not restart the connection to get the lost one back; that comes at the next start of the connection or a restart by hand. (D200)
- A button reset keeps no logs, snapshot, SMS archive or failure state; after a reset the link repair counts from zero. (R7b)
- It shows people on site nothing about a failure.
- Releases hold no built image: everyone builds an image from their own profile. (D96)
- The configurator loads nothing from outside its file, sends nothing anywhere and keeps nothing in the browser. (R58, R56c)
- It never builds a profile in a public GitHub repository, except a run the person marks as a test. (R54)
- The build on GitHub only leaves a download (R53); the agent skill flashes only after the person's yes to that flash (R59b).
- It builds for the MF289F only. Another router is a port in a fork, which `docs/porting.md` guides (R62).
- With Tailscale it is no exit node, has no Tailscale SSH and no Tailscale page in LuCI, and cannot be signed out from the chat; a button reset and a flash that does not keep settings make it a new entry in the account. (D144)

## How it works

**Build.** The official OpenWrt ImageBuilder puts the image together from the system packages, a few modem packages and the project's own files.
The settings of one router (address, WiFi, tunnel, passwords, notifications) live in a **profile**: a private profile may hold secrets, the generic one holds none.
Before the build a script fills the project's files with the values of the profile, so the same code gives either image.

**First start.** A flash and a button reset erase changes made on the router, but the files of the image stay.
At the first start a one-time script sets the network, WiFi, tunnel, firewall and passwords from them, so a reset brings back the configured router, not bare OpenWrt.

**Modem.** The network mode, the bands and the SMS store live in the modem's own memory, and an OpenWrt reset does not touch them.
So a start script checks and fixes them at every boot.
OpenWrt sets up the data connection over QMI (the modem control protocol), and the project's scripts use only AT commands (the modem's text commands), one at a time, under a shared lock; only the data session watcher (below) also speaks QMI, to restart a call that netifd does not know is dead.
The image ships the QMI handler of netifd (OpenWrt's network service), `qmi.sh`, with a few edits the build makes to the package's file: the line that scans the network for 26 s at every start of the interface is gone, so a start takes about 15 s instead of about 40 s, and the handler sets up the IP versions as the next paragraph says. The build stops when the package's file is not the one the edits were made for. (R12d, D82, D172)

**IP versions.** The internet comes in two versions, IPv4 and IPv6, and an operator may give either or both.
In the mode that uses both, the router asks for both at every start and uses what the operator gives; on a SIM that gives IPv4 only, as the owner's does, it asks for IPv6 right after the IPv4 call is up, the refusal costs about a second, and the link stays on IPv4.
Where an operator gives IPv6 only, as some French operators do, the router still gives the devices IPv4 by a translation through the operator (464XLAT); when the operator gives IPv6, the WiFi devices get it too, behind the router's firewall, and otherwise the LAN stays IPv4 only.
The link checks and the repair count an answer over either version, so a working IPv6-only link never looks dead.
0.7.0 ships with IPv4 alone as its default, and the owner switches the mode that uses both on in LuCI without a new image; that mode becomes the default once it has run on an MF289F with a SIM that gives IPv6, best one that gives both, and LuCI can also force IPv4 or IPv6 alone.

**Data session watcher.** When the mobile network detaches the modem and the modem attaches again by itself, netifd keeps showing `wwan` as up, but the call of the modem is dead and nothing in OpenWrt notices.
The service `lw-linkwatch` asks the modem every 5 s whether the call is up, and when it is lost with the modem registered, it starts the call again on netifd's own QMI client and renews the DHCP lease, about 2 s in all.
After 20 s without success it runs `ifup wwan` once and leaves the rest to the repair below.

**Link repair.** Watchcat, an OpenWrt tool to which the image adds a check of both IP versions, restarts the LTE connection itself, by default after 2 minutes without internet (the profile sets the wait, and always keeps it short enough for this restart to come before any restart of the whole router).
The script `wwan-recover` checks the internet every 5 minutes and, when restarting the connection does not help, restarts the whole router on a ladder of growing gaps.
It also recognises a used-up package (only the operator's DNS answers) and a SIM locked with a PIN, and then stops restarting sooner, because a restart does not help.
When a restart did not bring LTE back but the package is there, the router turns on EDGE until the next restart; a failure ends only when LTE works again.

**Ways to build.** Every way starts from the same profile, and `build.sh` decides whether a profile is valid. A build on GitHub also needs both passwords set in the profile.
On a Linux machine the owner runs `build.sh` directly.
Without one, a person fills in the configurator, a web page in a single file that runs in the browser and sends nothing, and stores the resulting text as a secret of a private GitHub repository of their own, made from a small template the project offers.
A GitHub Actions workflow in that repository fetches the lonewrt release the person names, builds the image on GitHub's machines (runners), runs the tests, and hands back the image as a download (an artifact); the person flashes it in LuCI, or lets a coding agent do it.
A coding agent can lead through the same steps with the agent skill, uses the profile without showing its secrets in the chat, and flashes only when the person says yes.

**Tailscale.** Tailscale is a VPN service whose free plan joins a person's devices into one private network, their account. The devices find each other through Tailscale's servers, so it works even where the operator shares one public address among many SIMs (CGNAT) and nothing from outside can connect to the router.
With `TS_ENABLED='1'` the build adds the official OpenWrt package, which roughly halves the free flash.
A small service of the image sets Tailscale up at every start, and the router's firewall lets the owner's devices in but lets the router start nothing towards them; `docs/tailscale.md` shows how to make the account itself enforce the same, so even a stolen router reaches nothing.
A router with no Tailscale state (after a flash or a reset) asks Tailscale for a sign-in link, and the bot posts it once; whoever signs in with it adds the router to their account.
The bot then says how to connect and reminds the owner to turn off the end of the sign-in for the router, which Tailscale otherwise applies after some months.

## Key decisions

- **Configuration in the image:** a button reset brings back the configured router; in exchange, a lasting change of settings needs a new build and a flash. (D2)
- **LTE only, no automatic mode:** the router does not fall to 2G by itself and get stuck there, and with dead LTE it gets EDGE right after the first failed restart, at the cost of short breaks in access at the following restarts. This holds for the generic image too, with no switch in LuCI. (D3, D30)
- **Bands:** a profile can lock the bands that work at its site, because a modem may move from a strong band to a weak one; the generic image leaves the bands alone, because it does not know the site. (D4, D23)
- **Session watcher:** a data session dropped by the network is started again in place within seconds instead of after minutes of watchcat and a restart of the interface; in exchange the image has one resident script that asks the modem over QMI every 5 s. (D80)
- **Restart limit:** after the limit the router waits for the network or a person, instead of restarting for weeks when the package is used up. (D8)
- **Secrets in the private image:** the image is ready to flash with no further steps, but the image file and its profile must be guarded like a password and kept out of git. (D15, D20)
- **Generic image from the same code:** whoever gets it has all fixes, no secrets, a disabled tunnel and random passwords on a card handed over with the router; later images from the same profile keep those passwords. (D13, D21, D25, D36)
- **Building without Linux in your own private GitHub repository, no ready images:** a person gets an image of their own profile without a Linux machine, at the cost of a GitHub account that holds the profile's secrets; releases ship no image, because an image without a profile has no bot and gives everyone the same passwords. The configurator that writes the profile sends nothing, since its form holds those secrets. (D96, D97, D104)
- **A small template that fetches a release:** the person's repository holds only the workflow, so moving to a newer release is a new run with a new version number and no git work; the project keeps a second repository for the template. (D111)
- **Passwords set by the person for the GitHub build:** every run gives the same WiFi and root passwords, because a run on a fresh machine has no card to reuse; in exchange the person chooses the passwords and keeps the saved profile file, and gets no card with hints. (D112)
- **The agent may use a private profile:** the agent skill is the one exception to the rule that keeps agents away from private profiles; in exchange it never shows a secret value, and over the tunnel it flashes changed tunnel, band or mobile data fields only with someone at the router. (D115, D121)
- **Tailscale, joined by a link from the bot:** the owner reaches the router from their own devices without running a server, and the link needs no secret in the profile (a key for joining without a click is optional); in exchange it depends on Tailscale's servers and has about half the free flash, and every reset needs a new sign-in that leaves an old entry in the account. (D133, D134, D140, D145)
- **IP versions by what the operator gives, no profile key:** nobody has to know what their operator gives and every saved profile still builds; in exchange every start asks for IPv6 again, which may make the IPv4-only owner's start a little slower within a set limit, and the build edits more of OpenWrt's QMI handler, so an OpenWrt update that changes that file stops the build until the edits are checked against it. Until the mode has run on this router with a SIM that gives IPv6, 0.7.0 ships with IPv4 alone and the mode is switched on in LuCI, so an IPv6-only SIM needs that one change. (D168, D169, D172, D179, D184, D192, D202)

## Requirements

### Terms

Paths starting with `/` are on the router; the others are relative to the folder of this file.

- **profile**: the file `profiles/<name>.conf` with variables and an optional folder `profiles/<name>/` with files (SSH keys); `generic.conf` holds no secrets, a private profile may. The generic image (profile `generic`, `build.sh generic`) and an image from a private profile are `sysupgrade` images built from these profiles.
- **cycle**: one run of `wwan-recover` from cron, every 5 minutes.
- **session**, **family**, **auto** and **forced**: the session is what one start of the interface `wwan` sets up with the network, until the interface goes down; its families are the IP versions it carries, IPv4 and IPv6. Auto, forced IPv4 and forced IPv6 are the values of `network.wwan.pdptype` of the IP family rule (R73).
- **native IPv4**, **translated IPv4** and **IPv4 service**: native IPv4 is an IPv4 call the session got at its start, on `wwan0` with the lease of the child interface `wwan_4`; a session that got one and lost it still counts as one with native IPv4 (R76b, D200); translated IPv4 is IPv4 carried over the session's IPv6 by 464XLAT on a device of its own (R76); a session has IPv4 service with either.
- **cellular answer**: a reply to a ping that went out through the session's device for the address's family: from 8.8.8.8 or 1.1.1.1 through the native IPv4 device or the translation device, from 2001:4860:4860::8888 or 2606:4700:4700::1111 (the IPv6 addresses of the same two public DNS services, from: ../lonewrt-notes/ipv6/E-astra-report.md, section 2 "Probes", 2026-11-23) through the session's IPv6 device. A reply that came over another interface (the WireGuard tunnel, Tailscale, the LAN) is none.
- **family check** and **online**: the family check is one round of pings that, for each family the session has, pings that family's two addresses in turn and stops for that family at its first answer; it gives a result per family and a combined one. Each check that runs it keeps the packet count and time limit it has for its IPv4 addresses (watchcat by R14, `wwan-recover` 2 packets with a 3 s limit, and so on), and its IPv6 addresses get the same. Online is a cellular answer in one family check.
- **family lost**: a family of the session that got no cellular answer in 3 scheduled family checks of watchcat (R14) in a row while another family answered; family checks of other parts of the image do not count. It is a state the log reports (R77b), not a proof that the call is gone.
- **expert review**: ../lonewrt-notes/ipv6/E-astra-report.md, the design review of the IP family work of 2026-11-23, which decision rows D171 to D192 cite by finding and section; its recommendations are taken into the spec on the owner's go for the overnight work of that day. The **second expert review** is ../lonewrt-notes/ipv6/E2-astra-report.md, 2026-11-23, of this spec after its first read; decision rows D195 to D203 cite it by item, and its changes are taken in as rulings of the session that runs the work.
- **LTE-only mode** and **failure**: the router is in LTE-only mode when there is no EDGE marker in `/tmp` and `network.wwan.modes=lte`; a failure is the run of cycles from the first cycle that is not online to the first online cycle in LTE-only mode, so a cycle on EDGE belongs to the failure.
- **code** and **work folder**: `build.sh`, `src/` (scripts and templates), `profiles/` and `image/` are in this folder; the ImageBuilder and the downloaded packages are in the work folder, which `build.sh` takes from the variable `LW_WORK`, by default `work/` in this folder (ignored by git). `fetch-deps.sh` downloads everything there with pinned sha256 sums (D35).
- **limit** and **limit cycle**: the limit is the number of restarts from the limit rule (R19); the limit cycle is the first cycle that is not online after the restart that reached this number.
- **operator DNS** and **AT port**: the operator DNS is a DNS server the session gives: that of the native IPv4 lease (on the interface `wwan_4`), else one of the session's IPv6 settings; the AT port is `/dev/ttyUSB2` for the image's scripts and `/dev/ttyUSB1` for LuCI and manual work, both of the same modem.
- **`<r>`** and **`<ladder>`**: `<r>` is `ssh root@<router LAN address>` (the cable connection is in `README.md`); `<ladder>` is the recovery ladder tests `tests/ladder/`, run by `tests/run-all.sh ladder`.
- **`<tests>`** and **`<vm>`**: `<tests>` is `tests/run-all.sh`, which runs every test `tests/<area>/*.sh` in the official OpenWrt 25.12.6 x86_64 rootfs (the same busybox, `uci`, `jsonfilter` and coreutils `timeout` as on the router) under `bwrap`, with stand-ins for the hardware from `tests/stubs/`: an AT modem with a state model, `ping` and `nslookup` separately for LTE and EDGE, `logger`, `reboot`, `ifup`, the uptime. `<vm>` is `tests/vm/`: an image with the same files built for x86_64 and run in QEMU, with a stand-in AT modem on a serial port and a fake `wwan`. Neither of them imitates the ipq40xx hardware, QMI (apart from two `uqmi` stand-ins in `<tests>`: one for the watcher, and a stateful one with modem profiles, clients and calls per family, against which `<tests>` runs the image's `qmi.sh` derived from the cached `uqmi` package, R73) or the operator network.
- **operator preset**: a data file `/usr/share/lw/operators/<MCC-MNC>` with everything that belongs to one mobile operator (R47); the format is in `docs/operators.md`. The image ships `29702` (Telekom Montenegro); requirement texts quote it as the example. A profile can carry one more in its `OP_*` keys (R47d).
- **user's repository**, **workflow**, **run** and **artifact**: the user's repository is a GitHub repository that a person makes from the project's template repository (R53h); the workflow is its GitHub Actions workflow that builds an image, a run is one execution of it on a GitHub-hosted runner, and the artifact is the download a run leaves. `LW_PROFILE` is a repository secret of the user's repository that holds the text of one profile file.
- **release**: a lonewrt version published as a GitHub Release of the public repository with the tag `v<VERSION>` (R3b), for example `v0.1.0`.
- **configurator** and **agent skill**: the configurator is the HTML file of the configurator rule (R56); the agent skill is the instruction file for a coding agent of the skill rule (R59), at `skills/lonewrt/SKILL.md` (R59d).
- **secret values** and **run fixture**: the secret values of a profile are the values of `WIFI_KEY`, `ROOT_PASSWORD`, `ROOT_PASSWORD_HASH`, `WWAN_PASSWORD`, `WWAN_PIN`, `WG_PRIVATE_KEY`, `TG_BOT_TOKEN`, `HC_PING_URL`, `SMS_ADMINS` and `TS_AUTHKEY`, the keys `docs/profile.md` names as secrets or private data. The run fixture is `tests/build/fixtures/fake-full.conf` with its `@FAKE_...@` placeholders filled the way `tests/build/lib.bash` fills them, so `build.sh` accepts it.
- **tailscale image**, **account**, **fresh Tailscale state** and **added**: a tailscale image is built from a profile with `TS_ENABLED='1'`; the account is the private Tailscale network (tailnet) of the person who signed the router in; the router has fresh Tailscale state when `/etc/tailscale/` holds no state of a node, which is the case after every flash that does not keep settings (`sysupgrade -n`, LuCI without "Keep settings") and after every button reset, and stays so across restarts until a sign-in; the router is added while Tailscale reports it signed in to an account (backend state `Running`, see the interface facts of the Tailscale section).
- **sign-in**: a change of the router from not added to added; a restart of the router or of Tailscale is not one.
- **auth key** and **tag**: an auth key is a key made on Tailscale's admin page (`tskey-auth-…`) that signs a device in without a click; in a profile it is `TS_AUTHKEY`. A tag is a label such as `tag:lonewrt` that a device gets in the admin page or from a tagged auth key, the key that adds it; the account's access policy can name a tag in its rules (R71b).

### Build and profiles

- **R1:** The image is built with the official OpenWrt 25.12.6 ImageBuilder for `ipq40xx/generic`, device profile `zte_mf289f`, with the kernel and system packages of the official release (D1).
- **R2:** The image holds the packages of the "Included" table in `packages.md` and none of the "Left out" table; that table is binding (D14, D26). A row marked "only with `TS_ENABLED='1'`" is in a tailscale image only (R63). The packages of the table "Removed from the default set" are not in any image (D167).
  - **R2a:** The `.apk` files from outside the official feeds (group `extra` of `deps.lst`) go into the ImageBuilder only as `deps.lst` pins them: each listed file must be in `dl/extra` with its pinned sha256, checked by `build.sh` right before the copy, and `dl/extra` holds no other `.apk`. A missing, altered or unlisted file stops the build with the file's name. Before the copy, `build.sh` removes from the ImageBuilder's `packages/` the other versions of those same packages, matched by the exact package name (`modemband` is not `modemband-5g`), and nothing else; a package pinned twice in `deps.lst` stops the build with both file names (D77).

The value goes into `/etc/lw-build` (R7b) and into the summary line of the build (D94).

  - **R33b:** The root password can also be given in clear text as `ROOT_PASSWORD` (8 to 63 printable ASCII characters, as `WIFI_KEY`); the build hashes it the way it hashes a drawn one and writes only the hash into the image. When a card for the profile already exists, every build rewrites it from what the image holds, so it never names a password the image does not have: drawn values keep coming from the old card, a value the profile sets replaces the card's (`wifi=`, and `root=` with the profile's `ROOT_PASSWORD`), and for a profile that gives only `ROOT_PASSWORD_HASH` the card has no `root=` line and says that root uses the hash from the profile. When no card exists and nothing is drawn, no card is written. A rebuild keeps the password, not the hash: the hash gets a new salt each time, as for a drawn password. An image from a profile with `ROOT_PASSWORD` is private by the rule that holds for `ROOT_PASSWORD_HASH` (R4, D15). Neither the build output nor the image holds the clear text (D73).

### Ways to build

Someone without a Linux machine builds in the user's repository, with a profile written in the configurator; a coding agent follows the agent skill. The build itself is the one of the rules above.

- **R52:** A profile is the only input of every way to build: the workflow (R53), the configurator (R56) and the agent skill (R59) read and write profile files in the format of `docs/profile.md`, add no key that `generic.conf` lacks, and leave the decision whether a profile is valid to `build.sh` (R3), so a profile is accepted or refused alike on every way (D95). The one exception is the password rule of a run (R53i), which refuses a profile that `build.sh` accepts.
- **R53:** A run takes the whole profile from `LW_PROFILE`, builds the image from it with `build.sh`, runs the tests of the test rule (R53d), and only when all of them pass uploads one artifact with `<name>-sysupgrade.bin` and `<name>.manifest`; a run draws no password, so it writes no card (R53i). Which code a run builds and where `<name>` comes from is the run fields rule (R53j); how long the artifact stays is the artifact lifetime rule (R53g) (D97, D102, D113).
  - *scenario* given a user's repository whose `LW_PROFILE` holds the run fixture, when the person starts a run, then the run passes and its artifact holds the image and the manifest of that profile and nothing else
  - **R53e:** The artifact holds only the files of the run rule above (R53): never the profile, the rendered overlay, the ImageBuilder's output folder or a log.
  - **R53a:** A missing or empty `LW_PROFILE` stops the run with a message that names the secret and says where to set it; a profile that `build.sh` refuses stops the run with the message of `build.sh`, which names the key and never its value (R3). A stopped run uploads no artifact.
    - *scenario* given `LW_PROFILE` with the line of `LAN_IP` removed, when a run starts, then it stops with an error naming `LAN_IP` and leaves no artifact
  - **R53b:** The log, the summary and the annotations of a run hold none of the secret values of the profile: the workflow never prints the secret, the profile file or the rendered overlay, a failed test or build shows no such value, and GitHub's hiding of secret values in the log is not counted on.

### IP families of the LTE session

A start of `wwan` asks the network for a session and uses the families the operator grants.
These rules hold for every start: after a boot, an `ifup`, a watchcat restart, the EDGE switch (R22) and the LTE probe (R23).
The stand-in modem of Terms models each operator below; the hardware each case was tried on is in Acceptance.

- **R73:** `network.wwan.pdptype` decides which families a start asks for: `ipv4v6` is auto, `ipv4` or `ip` forces IPv4, `ipv6` forces IPv6, in any letter case; a missing or other value forces IPv4, as the stock handler does. A value set in LuCI takes effect at the next start of the interface, with no new image (D168, D170, D171).
  - **R73a:** Auto runs the steps of the table below in order and stops at the first step that gives a session; forced IPv4 runs only step 2, forced IPv6 only step 3. A call counts as granted only when it started with a numeric handle and reads connected (R73e); any other outcome (a refusal, an error text, no answer in time, a failed family selection) counts as refused; the MF289F accepts the family selection for both families (measured: `uqmi --set-client-id wds,<cid> --set-ip-family ipv4` and `ipv6` on a spare client, rc 0, owner's router, 2026-11-23). The table binds (D169, D171, D178).

| Step | Modem profile type | Calls, each on its own client | Session |
|---|---|---|---|
| 1 | `IPV4V6` | IPv4, then IPv6 | both granted: dual stack; only IPv4: IPv4 alone; only IPv6: IPv6 alone with translated IPv4 (R76) |
| 2, when both calls of step 1 were refused | `IP` | IPv4 | IPv4 alone |
| 3, when step 2 was refused | `IPV6` | IPv6 | IPv6 alone with translated IPv4 (R76) |

### IPv6 on the LAN

The LAN is `lan`, the one LAN of the image. A global prefix is an IPv6 prefix of the operator that the network routes to the router.

  - **R14a:** `LINK_RESTART_AFTER_S` is a key of every profile: a whole number of seconds from 120 to 900, written as the `period` of the watchcat entry `wwan_soft`; nothing else of that entry (mode, interface, hosts, ping period of 60 s) depends on the profile. ### EDGE fallback

The fallback puts the modem into automatic mode; on networks that run only 2G next to LTE, this means EDGE.

- **R22:** When the failure state has at least one restart from the ladder and is not passive, 10 min have passed since the start, the router is not online and the last class is not `account` or `sim`, the router switches the modem to automatic mode (`network.wwan.modes=all` and `AT+ZSNT=0,0,0`) and brings `wwan` up again, at most once per start. In the cycle in which the failure reaches the limit, the router first settles the limit (R19), then the switch to EDGE by the passive mode rule (R22a) (D30).
  - *scenario* given dead LTE (ping and operator DNS silent) and ping and operator DNS working on EDGE, when 250 cycles pass, then there are 6 restarts, the saved limit class is `hang`, and the router stays on EDGE
  - **R22a:** In passive mode, from the limit cycle on and after every start, the router switches to EDGE when 10 min have passed since the start and it is not online, at most once per start, not counting the return after a failed LTE probe (R23), unless the saved limit class is `account` or `sim` (D32).
    - *scenario* given a failure state after the limit with class `hang` and a fresh start of the router, when 10 min pass without being online, then the router switches to EDGE exactly once
- **R23:** Before the limit, EDGE lasts until the next restart from the ladder. After the limit the router, every 72 cycles on EDGE, online or not (6 h), tries LTE-only mode: it removes the EDGE marker, sets `network.wwan.modes=lte` and `AT+ZSNT=6,0,0` and brings `wwan` up, so the probe cycles are cycles in LTE-only mode. An online probe cycle ends the failure when a read of `AT+ZSNT?` confirms LTE-only mode; 2 probe cycles that are not online or lack this confirmation go back to EDGE, unless the class from the probe is `account` or `sim` (D30, D41).
  - **R23a:** After the limit the router on EDGE does not restart, even when EDGE goes away (D30).
    - *scenario* given the router on EDGE after the limit, when there is no online cycle for 100 cycles, then there is no restart
- **R24:** A router restart always ends the EDGE fallback, and the router comes up in LTE-only mode by the modem state rules (R10, R11); it goes back to EDGE only by the EDGE rules (R22, R22a) (D12).
- **R25:** When the saved limit class is `account`, the router never switches to EDGE, even after a restart; when the package runs out while the router is already on EDGE, the router leaves EDGE at the next restart from the ladder (D24).

### Tailscale

This section holds only for a tailscale image; an image with `TS_ENABLED='0'` has no part of it (no package, zone, service, `/status` line or SMS command), and the other requirements pass unchanged; the one answer such an image gives about Tailscale is in the command list (R37). Tailscale's own rules used here (from: Tailscale docs "Key expiry", `tailscale.com/kb/1028`, and "Auth keys", `tailscale.com/kb/1085`, read 2026-11-22): a device's sign-in ends after 180 days unless key expiry is turned off for it; a device added with a tagged auth key has key expiry off; an auth key lives 1 to 90 days, and a device added with it stays added after the key expires.

The image relies on these fields of Tailscale's state as `tailscale status --json` gives it (guess; Unverified); which commands read the state and ask for a link is the builder's (Builder decides):

- `BackendState`: `NeedsLogin` is not added (after the router was added: the sign-in ended or the router was removed), `Running` is added, `Starting` is starting, and `Stopped` or no answer from the daemon is not running.
- `AuthURL`: the sign-in link.
- `Self.DNSName`: the router's name.
- `Self.KeyExpiry`: the date the sign-in ends, absent while key expiry is off for the router.
- `Self.PrimaryRoutes`: the approved route.
- `CurrentTailnet.Name`: the account.

- **R34:** Every new SMS in the modem store reaches the chat `TG_CHAT_ID` as a message with the sender in bold, the modem's time and the full text in a quote, within 30 s of appearing in the store when the router has internet; the exception is balance replies, which follow the balance rule (R36) (D43, D46).

  - **R34c:** A normal pass writes nothing to syslog or flash; flash is written only for a new SMS or a sent message, and syslog gets at most one entry per change of the sending state (works or does not work), with the tag `lw-notify`.

  - **R34e:** Latin-1 characters (such as `é`, `ü`) that `sms_tool` returns as single bytes instead of UTF-8 reach the chat as the same characters; Telegram rejects such a raw byte with `HTTP error 400`.

A rejection is not reported as a lost link (R34c).
  - *scenario* given an SMS with the byte `E9` in its text and a second SMS after it, when the router has internet, then the chat has both, the first with `é`, in the order they arrived

  - **R46d:** SMS control also works in an image without Telegram keys when the profile sets `SMS_ADMINS`; an empty `SMS_ADMINS` turns it off (R38a then covers both: without Telegram keys and without `SMS_ADMINS` the service does not start).

## Decisions

| ID | Decision | Why |
|---|---|---|
| D1 | Official ImageBuilder 25.12.6 instead of a third-party build such as eko.one.pl (R1) | a stable release and a reproducible build |
| D2 | The configuration lives in the image (R7, R31, R31a) | a button reset must bring back a working router, not bare OpenWrt |
| D3 | LTE only, automatic mode rejected (R10, R11) | a modem that falls back to EDGE does not return to LTE by itself |
| D4 | Band lock per profile (R11c) | a modem may move from a strong band to one that is weak at the site, and data then stalls |
| D5 | AT instead of QMI in the scripts (R12a, R12c), with one exception, D80 | killed `uqmi` calls used up the modem's QMI client IDs and blocked bringing `wwan` up |
| D6 | Watchcat plus the project's own `wwan-recover` (R14, R15) | watchcat cannot grow the gaps between its actions, so the script only does the router restart |
| D7 | A ladder of growing gaps (R16) | short failures get a quick restart, and a long one does not restart the router all day |
| D8 | A limit of 6 restarts per failure (R19) | a used-up account must not drive the router into restarts for weeks |
| D9 | A cycle counter instead of time (R21, R21e) | the router has no RTC, and after a restart without NTP the clock goes back |
| D10 | The failure class never holds a restart back (R18a) | the modem can report a connection while data is stuck |
| D11 | No step between the `wwan` restart and the router restart (R16) | `AT+CFUN=1,1` and a USB unbind restart the whole board anyway |
| D12 | The EDGE fallback ends at a restart (R24) | a person who restarts the router gets plain LTE back, and the EDGE rules decide again |
| D13 | The generic image has no secrets and no data of a private profile (R4, R4a) | the generic image is meant to be shared; a built image carries its WiFi password and root hash, so the repository is shared, not a built image, and each router gets its own build |
| D14 | Packages modemdata and modemband (R2, R30a) | operators can lock the modem onto one band, so LuCI must show and set the bands and the signal |
| D15 | A private image holds its profile's secrets and stays out of git (R5) | the image is ready to flash with no further steps, and the repository never holds secrets |
| D16 | Automatic SMS cleaning (R26) | a full SMS store stops delivery |
| D17 | Signal log (R28) | a record of the signal makes link failures diagnosable afterwards |
| D19 | HTTPS for LuCI (R30) | the root password does not cross the WiFi in clear text |
| D20 | The profile is a file of variables; `generic.conf` is in git, other profiles are ignored (R3, R5) | one parser checks every key, and private profiles stay local |
| D21 | Defaults of the generic image and random passwords (R7a, R33) | a fixed password in a public repository is known to everyone who reads it |
| D22 | Taking over a dead `wwan-recover` lock (R21a) | without it one killed process turns the repair off until the next restart |
| D23 | The generic image does not force bands (R11c) | a band mask fits only one site |
| D24 | No EDGE when the package is used up (R25) | after a top-up the router should be on LTE at once |
| D25 | WireGuard disabled in the generic image (R7a, R32) | the template knows no server to connect to |
| D26 | Package wifischedule (R2, R30a) | the WiFi can be switched off on a schedule from LuCI |
| D27 | APN from the profile, otherwise empty, and the operator table only as fallback (R13, R13a, R13b) | the APN is not stored on the SIM, and an empty APN lets most networks assign their own |
| D28 | Bands and IMSI through the project's own AT commands on the scripts' port (R12) | `modemband.sh` and a fallback IMSI read used the LuCI port and bypassed the lock |
| D29 | The wait for the lock counts toward the command's limit (R12b, R13c) | the APN script runs while the link comes up, and a hotplug script stuck on an AT command can take the router down |
| D30 | EDGE after the first failed restart, a failure ends only on LTE, LTE probes only after the limit (R15, R16, R22, R23, R23a) | a failure that a restart did not fix is a failure of the LTE network, not of the modem, so waiting for the sixth restart before EDGE means almost a day without access |
| D31 | Class `account` from an operator DNS answer, only for cycles in LTE-only mode, limit class saved in the state (R18, R18b, R18c) | with a used-up package the operator DNS answers, while "nothing comes back" depended on whether someone was using the WiFi |

| D33 | The snapshot does not wait for a busy AT lock (R20a) | the restart must not depend on the modem that is suspected of hanging |
| D34 | APN fallback from the second failed attempt, with the "from table" marker, in the background (R13b, R13d) | the first attempt with an empty APN fails also on networks that accept it, and a script blocking in hotplug can hang the router |
| D35 | Code, profiles and images in this folder, the ImageBuilder in the work folder (R3, R5) | the sources stay small and versioned, and the heavy downloads stay out of the repository |
| D36 | A password card with hints, passwords repeated between builds (R33, R33a) | after a reset and after a later image the router still has the passwords of the card that came with it, and its behaviour is explained there, not in syslog |
| D37 | Image identity and a first-start entry (R7b) | a reset erases logs and state, so without it a router after a reset cannot be told from one without a failure, nor can the image version be known |
| D38 | Class `sim` for a SIM without `READY` (R18, R18d) | a restart does not enter a PIN, and a SIM with a PIN otherwise gives a day of restarts without a message |

| D64 | A persistent bot keyboard, with the bot's privacy mode on (R37e) | a non-technical person taps instead of remembering commands, and the bot still receives only commands and replies to its own messages, not the rest of the group conversation |

| D68 | Commands in SMS replies and in `README.md` in lower case (`status`, `reboot`); the router takes any case (R46a) | upper case suggests that commands must be typed in upper case |
| D69 | An SMS reply goes to the number from `SMS_ADMINS` without `+` (R46) | `sms_tool` 2025.08.23 encodes `+` as a digit, so the network accepted replies to `+<number>` that never arrived; a number of 6 or more digits goes out as international anyway, and a national sender form has no country code |

| D79 | The wait before watchcat restarts `wwan` is a profile key, `LINK_RESTART_AFTER_S`, a whole number from 120 to 900 with the default 120 (R14, R14a) | on 2026-11-10 the operator dropped the data session while the modem stayed registered, nothing showed in the logs, and with the earlier fixed 300 s the outage was about 6 min, almost all of it waiting for the restart that brought the link back within 40 s. The default 120 s halves that; the cost is an interface restart, about 15 s without internet since D82 (about 40 s while qmi.sh still scanned the network), on a glitch that would have healed alone. Lower bound 120 s: the ping period is 60 s, so two failed pings in a row. Upper bound 900 s, checked for two cases. A failure that starts after boot: the first router restart is at the 6th failed cycle, at the earliest 1500 s after the outage begins (R16, 6 cycles of 5 min counted from the first failed cycle); watchcat restarts at most 920 s after the drop (60 s steps counted from the last answer, plus the pings), the link is back about 15 s later (about 40 s before D82), so 565 s remain. A failure already there at boot: watchcat counts only from uptime 900 and restarts at about 1820 s, the link is back at about 1835 s (1860 s before D82); wwan-recover counts cycles only from uptime 600 (R17), so its 6th cycle, the router restart, is at 2100 s at the earliest, and 265 s remain (240 s before D82). With 1200 s the boot case would restart the router first (the interface restart would come at about 2420 s), which is why the bound is 900; the highest value that still passes the boot case is about 1030 s (1020 s before D82). The earlier 300 s was far from this edge (link back after about 415 s) |
| D80 | In-place restore of the data session by polling, in `lw-linkwatch`, with `ifup wwan` only after 20 s (R49 to R49g, R12c) | measured on the MF289F (OpenWrt 25.12, qmi, uqmi 2025.07.30) on 2026-11-10: three times the network detached the modem with a re-attach request (`AT+CEER`: "Nas detach with reattach, LTE network detach") and within about 5 s the modem was registered again with a new address in context 1, but for the host the call stayed dead: the data status was `disconnected`, the settings on netifd's client `Out of call`, `registration` still `registered`, while `wwan0` kept the old address and its carrier, netifd showed `wwan` up, and the modem did not start the call by itself in 20 s although netifd started it with `--autoconnect`. The same state comes from `AT+CGATT=0` then `AT+CGATT=1`. A `start-network` on netifd's client answers in 0.2 s with the same handle as `pdh_4`, a release then a renew of `udhcpc` gives the new lease in the same second (a renew alone 13 s: it asks the old server first; the renew must wait for the release, because two pending signals arrive USR1 first, see R49c), and ping works about 2 s after the call; a full `ifup wwan` takes 32 to 40 s here (qmi.sh scans the network for 26 s because `network.wwan.modes` is set; on 2026-11-11 the same `ifup` to the first good ping took 40,5 to 46,5 s, and 14,2 to 14,8 s with the scan line removed, D82) and watchcat comes after 120 s at the earliest, so the outage was about 6 min before D79. ## Risks

- A bad image on the MF289F: recovery is only over UART with the case opened (`docs/development.md`, "Recovery"), so every image passes `sysupgrade -T` before a flash.
- Flash wear from the persistent log: the log has 1 MB with rotation, the signal log is in RAM, cron does not log job starts, and the failure state is written only on a change. During test days the log grew to about 570 KB in a day and a half, more than half of it netifd entries from manual `wwan` restarts; that is hundreds of KB a day on UBIFS with wear levelling. In a long failure 2 MB of log with the `.old` file hold only a few days of history.
- Flash wear at the debug level (R29c): about 55 KB a day for the signal samples (288 lines of about 190 bytes), about 30 KB a day for the heartbeat (288 lines of about 100 bytes), a dozen lines of about 100 bytes for each lost session, and one or two lines per pass while uqmi gives answers that are neither healthy nor lost or calls fail (the answer, and the failed call itself; 12 to 24 a minute, about 1,7 to 3,4 MB a day, in the worst case of a modem that answers garbage for days, so the log rotates once or twice a day). The log is twice as large, so the `.old` file goes out later and each rotation writes twice as much. A debug image is for a test period of days to weeks, then a rebuild with `LOG_LEVEL='info'`.
- QMI clients on the modem: the watcher's calls now run on netifd's own IPv4 client (R49b), but a start of the interface takes and releases more clients than before (R73e), and a call killed by its timeout may leave one allocated; D5 records what killed calls did to the client IDs before. Nobody has counted the clients on the router after a week of reconnects (Unverified).
- A used-up package: the image cannot fix it, it only recognises it and stops restarting sooner; the warning comes from the heartbeat on the server side.
- Flashing over the tunnel: a mistake in the tunnel or band fields of a profile cuts the router off until someone is on site, so an image with changed tunnel fields is flashed only with someone at the router.
- The operator changes bands or priorities: the band mask is in the profile, and the signal log shows the change.
- The bot token in a private image: whoever gets the image file or the router can write as the bot and read commands; the bot has only reading commands (R37a), and the token is changed in @BotFather and with a new build. The token is also visible in the arguments of the `uclient-fetch` process during a request, that is to every process on the router, but not in the logs. The address of the healthchecks.io check (`HC_PING_URL`) is visible the same way, in the arguments of the `uclient-fetch` process every 5 min; whoever reads it can send false signals that the router is alive, which hides an outage, and can do nothing else with it.
- Every profile secret stays readable in the image's read-only part for whoever holds the router or the image: the tunnel key, the SSH host keys, the WiFi password, the root password hash, the APN password, the bot token, the heartbeat address and the Tailscale auth key (its file rule, R64b, limits who on the running router reads it, not who holds the router or the image). First boot deletes `zz-lw-config` only from the writable layer. The router stands among strangers, so the limit is set on the WireGuard server: the router's peer gets only its own tunnel address and may not open connections into the owner's network.
- Another modem firmware: the SMS store size, the `ZSNT` codes and the receive store falling back to `SR` were measured on `BD_TMOPLMF289F1V1.0.0B03`; on another firmware they must be measured again, and the requirements win over the modem's behaviour. The same holds for the dropped network scan (R12d, D82): the generic image drops it for every firmware of the MF289F, and on another one the scan after a mode change may matter.
- The build needs the package feeds of the ImageBuilder (network) for `uqmi`, before `make image` and in the VM bench (R12d); the `uqmi` package of the feed can change at an OpenWrt point release, and then the build stops if its `qmi.sh` lost the scan line or changed, instead of shipping a stale copy.
- The watcher's escalations have no brake (decided, not built): `lk_escalate` is not counted by the brake of R49e, so when the network drops the session again after every `ifup` and the restore in place fails each time, the watcher runs one `ifup wwan` per incident without end, about every 40 s now that an `ifup` takes 15 s (65 s before D82), and each one writes an `Auto-APN` line and some netifd lines. A limit was rejected: one `ifup` per incident is the best action left when the restore in place fails, and a brake would trade outages of about 20 s for outages of up to 120 s. Since the escalation marker holds only for its own session (R49d), a session that is born dead after every `ifup` also gets one `ifup` per start, with no healthy pass in between. Next check: the log the first time it happens.
- The last advertisement of the LAN falls short of R74c (decided, not built): in the pinned odhcpd, switching the LAN's advertisements off sends one last advertisement with no prefix in it, whose default-router lifetime is zero only when the default route is gone; with another IPv6 default (a WireGuard `::/0`, a wired `wan6`) it keeps 1800 s, up to 30 min of a dead IPv6 default for the LAN, and the old prefix is not deprecated in it, only by the cap of R74c (measured in `<vm>` by a packet capture, 2026-11-24; from: slice 3a review, ../lonewrt-notes/ipv6/P3a-review.md, Q5). A route lost with no interface event does not reach the LAN either. This touches only a router with auto selected and blocks auto as the default (R73k). Next step: a one-shot advertisement that carries the old prefix with preferred lifetime zero.
- A loss of the IPv6 call inside the modem has no producer for R74f (decided, not built): no part of 0.7.0 reads the IPv6 call's state, and such a loss gives no netifd event, so the LAN keeps advertising a dead default until the next interface event, which may be hours away; browsers cope, plain clients hang on IPv6 connects (from: slice 3a review, Q5). It blocks auto as the default (R73k). Next step: a later piece of work in which `lw-linkwatch`, which already reads the modem while `wwan` is up, reports a confirmed loss of the IPv6 call to the LAN.
- `apk upgrade odhcpd-ipv6only` on the router brings back the stock init script (R74g): the LAN quietly has no IPv6 until the next flash, while IPv4 and DHCPv4 work on. `docs/network.md` says so.
- Writes to the modem's memory in auto (R73f, R73n): a SIM that refuses every call writes profile 1 up to four times per failed start (`IPV4V6`, `IP`, `IPV6`, the rollback) for as long as netifd starts again, against one write in the stock handler, and a SIM that refuses `IPV4V6` and grants `IP` writes profile 1 and the flash record twice at every start; forced IPv4 writes less than stock (from: slice 2a review, ../lonewrt-notes/ipv6/P2a-review.md, risk 3). This happens only with auto selected in LuCI. Next check: the number of writes per start before auto becomes the default (D202).
- The IPv6 result reaches the session watcher only after watchcat's next scheduled check (R14g), which runs every 60 s and may take 40 s, while the watcher decides at 20 s (R49d); on dual stack the watcher therefore nearly always logs `IPv6 kept, no ifup`, and a session with both versions dead waits for watchcat's silence timer (120 s or more), which D200 allows. Next check: the log of the first dual-stack SIM; if the wait matters, the watcher runs one IPv6 check of its own at 20 s.
- A failing interface start is retried by netifd (a registration timeout, a refused call) about 2,7 times as often, every 15 s instead of every 40 s (D82; six failed starts 15 s apart in the measured EDGE fallback with LTE absent). Each attempt writes about 20 log lines of about 90 bytes, roughly 10 MB a day instead of 3,9 MB (an estimate from the line sizes, not measured), so the 1 MB log rotates about 10 times a day and keeps a few hours; each attempt also starts one detached `lw-apn`, which leaves the AT port alone when the APN comes from the profile. No backoff is built; a case seen in the field decides whether one is needed.
- The artifact of a run holds a private image, which holds the profile's secrets: whoever can read the user's repository can download it while GitHub keeps it, 90 days unless the workflow sets less (from: GitHub docs, "Downloading workflow artifacts" and "Store and share data with workflow artifacts", read 2026-11-16), so its collaborators are people the person would give the router's passwords; the workflow keeps it 7 days (R53g).

The link goes only to the chat of `TG_CHAT_ID`, to SMS admins and over SSH; a router in the wrong account goes back to a fresh state with a button reset.

Next check: the resident size of `tailscaled` after a day on the owner's router.
- A tailscale image depends on Tailscale's servers for every sign-in and for finding its peers.
- Whoever has root on the router (a stolen router through failsafe or the serial port) can copy `/etc/tailscale/` and join the owner's account as the router; the account's default access rules let every device reach every other (from: Tailscale docs, "Access control", `tailscale.com/kb/1018`, read 2026-11-22), so that reaches the owner's other devices.
